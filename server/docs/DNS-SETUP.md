# Настройка DNS у регистратора

Чтобы dnstt работал, запросы вида `*.t.example.com` должны доходить до вашего VPS по UDP/53. Для этого домен (или его поддомен) нужно **делегировать** — указать, что authoritative NS для него находятся на IP вашего VPS.

## Что делегировать: домен или поддомен

Проще всего **делегировать поддомен** (например, `t.example.com`), а основной домен оставить как есть (на DNS регистратора или Cloudflare). Вы не теряете почту/веб-сайт, а трафик туннеля идёт через изолированную зону.

**Важно:** `t` должен быть коротким — каждая DNS-метка ограничена 63 символами, а dnstt пишет данные в **субметки** до основного домена. Чем короче основной домен, тем больше места для полезной нагрузки.

Хорошо: `t.example.com` (18 символов)  
Плохо: `my-very-long-subdomain.my-very-long-root-domain.com` — снизит throughput.

## Какие записи создать

Допустим, ваш домен — `example.com`, поддомен для туннеля — `t.example.com`, публичный IP VPS — `203.0.113.7`.

### 1. A-записи для будущих NS-серверов (в зоне `example.com`)

```
ns1.t.example.com.    A    203.0.113.7
ns2.t.example.com.    A    203.0.113.7
```

Разные имена (`ns1`, `ns2`) нужны потому, что большинство регистраторов требуют **минимум два NS**. Оба могут указывать на один и тот же IP — это работает.

### 2. NS-делегирование поддомена (в зоне `example.com`)

```
t.example.com.    NS    ns1.t.example.com.
t.example.com.    NS    ns2.t.example.com.
```

Так регистратор говорит «за зону `t.example.com` отвечают эти NS» (которые указывают на ваш VPS).

## Примеры настройки в панелях

### Cloudflare

Cloudflare не принимает NS-записи внутри собственной зоны через стандартный UI, но можно сделать так:

1. Создайте A-записи `ns1.t` и `ns2.t` → `203.0.113.7`. **DNS only (серая тучка)**, не proxied!
2. В «DNS → Records» добавьте две NS-записи для `t` → `ns1.t.example.com.` и `ns2.t.example.com.`. Cloudflare покажет предупреждение, нажмите «Override».

Важно: DNS-проксирование Cloudflare (оранжевая тучка) **несовместимо** с dnstt — отключите его для поддомена.

### Namecheap / REG.RU / Timeweb / другие

1. Зайдите в управление DNS домена `example.com`.
2. Добавьте две A-записи (`ns1.t` и `ns2.t` → `203.0.113.7`).
3. Добавьте две NS-записи для хоста `t` → значения `ns1.t.example.com` и `ns2.t.example.com`.

Если регистратор использует собственный интерфейс (не BIND-подобный), ищите «Host records» → «Add record» → type «NS».

## Проверка

После сохранения записей дайте зоне 5–30 минут на распространение, затем:

```bash
# Убеждаемся, что делегирование прописано корректно
dig +trace t.example.com

# Должно вернуть NS-записи ns1.t.example.com, ns2.t.example.com,
# и в последней части — обращение к вашему IP 203.0.113.7.

# Проверка через DoH — запрос должен дойти до вашего dnstt-server
dig TXT random123.t.example.com @1.1.1.1

# В journalctl -u dnstt-server появится лог о неопознанном клиенте
# (т.к. random123 — не валидные данные dnstt). Это нормально и означает,
# что DNS работает.
```

Альтернативно — специализированные проверялки:

- https://www.whatsmydns.net/ — смотрит NS-записи из разных точек мира
- `dig @8.8.8.8 NS t.example.com` — отдельно для Google DNS

## Если делегирование не работает

- Проверьте **glue records** у регистратора (`example.com` → Registrar → Host records / Child name servers). Некоторые регистраторы требуют отдельно «зарегистрировать» имя `ns1.t.example.com` и привязать его к IP. Без этого NS-делегирование «сломается» на уровне рекурсии (resolver не узнает IP NS).
- Проверьте, что на VPS `iptables -t nat -L PREROUTING -n -v` показывает пробрасывание UDP/53 → `:5300`, и `dnstt-server` активен: `systemctl status dnstt-server`.
- Проверьте firewall: `ufw status` / `iptables -L -n` — UDP/53 должен быть открыт наружу.
- Пакетно: `tcpdump -ni any udp port 53 or udp port 5300` при тестовом `dig`.

## Почему нельзя без делегирования

Публичные DoH-resolver'ы (1.1.1.1, 8.8.8.8 и т.д.) — это рекурсоры. Получая запрос для `*.t.example.com`, они:

1. Спрашивают у root-серверов, кто авторитативен за `.com`.
2. Спрашивают у TLD-серверов `.com`, кто авторитативен за `example.com`.
3. Идут к этим NS и спрашивают, кто авторитативен за `t.example.com` — и **только если там есть NS-делегирование на ваш VPS**, запрос дойдёт до вас.

Без шага «NS на ваш VPS» публичный resolver не будет слать запросы на ваш IP — никакой магии.
